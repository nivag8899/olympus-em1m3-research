# rec00（15MB "6-bit 编码区"）解包与逐 chunk 侦察（v1.6 固件，2026-10-09）

> 依据：`tools/split_rec00.py`（本次新写，改造自 split_arm_chunks.py）+ PIL/numpy 图像侦察 +
> section_00 交叉引用扫描。工作区 `firmware/work/arm/rec00_chunks/`（40 子块 + jpg/ 提取 + index.tsv）。
> 关联笔记：`em1m3-arm-payload.md`（§1 表中 rec00 的"15MB 6-bit 编码区"描述需要修正，见下）。
>
> **一句话结论：rec00 不是 ITRON/图像引擎代码载荷，而是一套"画面比例相关的图形资产库"——
> 29 张合成 JPEG 测试图（黑白边框图对、全白图、斜线目标）+ 10 张 120×160 LE16 软边沿剖面表
> + 1 块与 E-PL3 block 2 同签名的 6-bit 遗留数据（c00，仍未解）。消费者在主控（uITRON）侧。**

## 1. 子表 dump

rec00 文件：`rec00_0x43f00400.bin`，实际大小 **0xeffc00**（15,727,616 B；顶层表记 0xf00400 为对齐值，
按 trailer 自述 0xeffbc0+0x40；0x43f00400+0xeffc00 = 0x44e00000 与 rec01 恰好衔接）。
嵌套子表区 0x3e0（62 槽），**槽 0–39 共 40 条有效条目**（无越界、无垃圾槽需过滤），槽 40–61 全零填充。
所有条目无缝平铺 0x3e0..0x8809e0；其后 0x67f1e0 全零；文件尾 0x40 为标准双记录 trailer

## 2. chunk 清单与识别

**通用记录格式（c01 起所有 chunk）**：0x40 字节头（前 10 字节类别标签，其余补零）+ 净荷 @+0x40；
chunk 长度 0x200 对齐，净荷尾部补零。头部经验布局：`byte[6]` ≈ 尺寸/等级类，`bytes[7:9]` =
**画面比例码**（`03 02`=3:2，`03 04`=3:4，`04 03`=4:3，`06 06`=1:1，`10 09`=16:9，`ff ff`=特殊），
`byte[9]` = 子索引（JPEG 对里 00/01 = 极性；表块里 00/01 = 横向/纵向）。
同一头部标签不唯一（c13 与 c15 头 10 字节完全相同但分辨率不同），分辨率信息由子表长度隐含。

| 类别 | chunk | 识别 |
|---|---|---|
| **6-bit 数据** | c00 | 0x240000 B，熵 5.83，值域 0x00–0x3f（缺 0x3c），见 §3 |
| **大尺寸 JPEG 对（静止画全比例）** | c01–c10（5 对） | 5184x3456(3:2)、2912x3888(3:4)、5184x3888(4:3=原生)、3888x3888(1:1)、5184x2920(16:9)；sub00=黑底白边框图，sub01=白底黑边框图（互为反相），边框宽 ≈1–1.5% 边长 |
| **视频/小尺寸 JPEG 对** | c11–c16（3 对） | 640x480、1280x720、1920x1080（HDMI/视频档），同样黑白边框对 |
| **小尺寸 JPEG 对（全比例）** | c17–c26（5 对） | 1024x688(3:2)、576x768(3:4)、1024x768(4:3)、768x768(1:1)、1024x576(16:9)，黑白边框对 |
| **特殊三联（ff ff 比例码）** | c27–c29 | 2496x1920 白底+微弱竖线段、2496x1536 近全白、4096x256 白底+稀疏细斜线段（合成目标图） |
| **LE16 剖面表（5 对）** | c30–c39 | 各 0x9800：0x40 头 + 120×160 LE16（19200 值，值域 ≤1027）。sub00=**横向**软边沿剖面（梯形窗：升 44/平台 72/降 44，周期精确 160），sub01=**纵向**剖面（中部行全亮、上下渐暗）。比例码与 c01–c10 一一对应；3:4 表平台 [60..99] 比 3:2 表 [36..123] 窄（竖幅吻合） |
| 零填充 | 尾部 0x67f1e0 | 无未编索引数据（表后 leftover 全零） |

**JPEG 指纹（29 张全同）**：JFIF 1.01、density 1x1、baseline、**两张全 1 的 DQT（quality 100）**、
libjpeg 默认 Huffman 表、4:2:2 (h2v1) 采样 —— 离线脚本（libjpeg/PIL 类工具）批量生成，
**不是 TruePic 机内编码器产物**；每 chunk 恰含 1 张 JPEG（SOI@+0x40，EOI 近尾部）。
图像内容为纯合成图案（黑/白底+边框、细线段），非照片。

**无压缩流**：全部 chunk 均无 zlib/lzma/gzip/xz/lz4/zstd 魔数，直接解压 0 成功
（高熵 JPEG chunk 的 6.8–7.6 熵是 JPEG 本身的熵，非独立压缩层）。
**无 ARM/MN103 代码特征**：全库 0 个 `00 00 a0 e1` NOP sled、0 个向量表、0 个 `b .` 循环
（split 日志里的 "ARM-cond-density" 标签是弱启发式的假阳性——该判据接受 15/16 的随机字，
JPEG/6-bit 数据也能命中，勿采信）。

## 3. c00：6-bit chunk 特征与 E-PL3 对照

- 0x240000 字节，**100% 值 ≤0x3f**，实际用到 63/64 个值，**唯缺 0x3c**（提示 0x3c 为转义/标记码）；
  熵 5.833 bit/byte；值直方图平滑单调下降（0x2 最多 110k 次，0x0 次之）。
- **与 E-PL3 block 2 签名完全一致**：同长度 0x240000、同值域 0x00–0x3f（缺 0x3c）、
  同"表内地址 = 基址+0x400、净荷 @0x3e0"布局（E-PL3: header 两词 0x00240000/0x43d00400）。
  E-PL3（2011，MN103 主控、无 A9）到 E-M1 III（2020）原样携带 —— 该 6-bit 块是**跨代共享资产**，
  不可能是 A9 ITRON 代码。仓库无 E-PL3 镜像字节，无法做逐字节比对（开放问题）。
- 本次新增排除项：按位置 mod 2/3/4/6/8 的值分布无差异（非简单按位打包）、
  前 64k 值流自相关无任何 >0.25 峰（无周期结构）。zlib/lzma/gzip 直接解压均失败。
  与 E-PL3 前人结论一致："像 6-bit 编码但常见打包/压缩/delta 变换全被排除"。

## 4. ITRON-载荷判断（核心问题）

**rec00 内部：没有任何 ITRON/图像引擎代码证据。**

- strings 全库扫描 `itron/ID_TSK/tk_/TruePic/ISP/image/pipe/LUT/gamma/matrix/color/picture/jpeg/raw/v4l2/drv/task`：
  rec00 命中仅 JPEG 标准 Huffman 表中的 ASCII 段（`%&'()*456789:CDEFGHIJSTUVWXYZ...`），
  0 条 ITRON 任务名/错误串/内核名。
- 无 ARM/Thumb/MN103 指令密度特征（§2）。

**但 ITRON 本身在整个固件里证据确凿（均在 rec00 之外）**：

| 位置 | 证据 |
|---|---|
| 主控 section 0 @0x9e317e | `itronos` 内核名字符串 + `BFA_DLYTSK`/`SUS`/`SE_ACR`/`DELSEM`/`SIG`/`ISI` ITRON 服务调用名（附 2006 年 `$Id` 版本串） |
| 主控 section 0 @0x15e5cef | `uITRON Error Code` 错误码表（E_SYS/-5、E_NOSPT/-9 …）——**主 CPU 跑 uITRON** |
| 主控 section 0 @0x5df09 | 监视器命令 `load arm itron`（load2）；@0x5e09b 注释 `<arm load2> <--- load itron(master)` ——**A9 存在 ITRON 启动路径**，但对应载荷不在 rec00 |
| SCPU section 5 | `ID_TSK_*` ×16（ITRON 风格任务名，arch-map 已知） |

**消费者证据（主控侧）**：

- section 0 代码中 **0x43f00400（rec00 基址）立即数引用 ×40**（MN103 代码，分散于多个函数）。
- section 0 @0x14c369e 起有 **68 条 'Na' 区域目录**：`(0x10000 对齐地址 LE32, 'Na'+id+类字节)`，
  覆盖 0x42e40000–0x46a4ffff（含 rec00 全域），id 类 0x10/0x90 两段；紧邻 `N_GET_PULSE_DURATION`
  等监视器字符串——主固件对这段 ARM 地址窗口持有粗粒度资源索引。
- **唯一直接 chunk 级引用：0x446e0000 @0x14c3776**（'Na9002' 区域基址）= c27/c28/c29 + c30–c39 所在区。

## 5. 对「rec00 是什么」的结论与 3D LUT 落点意义

**rec00 = 主控显示/图形管线使用的一套"画面比例相关图形资产库"**：
每个画面比例（3:2/3:4/4:3/1:1/16:9）× 多档分辨率，备有黑白反相的边框测试图对（JPEG）、
软边沿横/纵向剖面表（LE16），外加三张特殊图案（竖线、空白、细斜线——疑似线缆/HDMI 输出校验或
快门/时序测量目标）。最可能的用途：EVF/LCD/HDMI 的比例遮罩与边框绘制、输出尺寸校验（工厂/自检）。
c00（6-bit 块）是从 E-PL3 时代继承的独立遗留资产，与其余 39 块不同族。

**对 3D LUT 项目的意义（多为排除性结论，但方向价值大）**：

1. **rec00 从"3D LUT 关键路径"上除名**：不是图像引擎代码、不是 ITRON 载荷、不是压缩固件。
   roadmap 任务 9 的"疑似图像引擎"假设证伪。
2. `em1m3-arm-payload.md` §8 的推论"rec01–08 参数表的消费者极可能是 rec00 解码后的图像引擎"
   **随之失效**——rec00 里没有引擎。rec01–08 曲线/矩阵表按 ARM 地址编址存放，
   消费者只能是**直接寻址这段共享窗口的主控 uITRON 固件（section 0）**。
3. 3D LUT 落点搜索应**全面转回主控侧**：section 0 有 `LUT`×15/`lut`×57/`gamma`×9/`color`×166/
   `matrix`×15 字符串与 40 处 rec00 基址引用——色彩科学就在那里；rec01(rec04 BE-float 系数)
   的引用者也要在 section 0 里找。
4. 附带修正 `em1m3-arm-payload.md` §1：rec00 不是"15MB 6-bit 编码区"——只有 c00（2.25MB）是 6-bit，
   其余 ~5.6MB 有效数据是 JPEG 图形资产（尾部 ~6.7MB 为零填充）。

## 6. 下一步

1. **section 0 反汇编**（MN103，可复用 E-PL3 binutils/Reko 路线）：从 40 处 0x43f00400 引用和
   'Na' 目录交叉定位资源装载函数，确认 JPEG/剖面表的具体消费路径（显示/自检/工厂模式）。
2. **3D LUT 主攻方向转移**：在 section 0 里定位 `gamma/LUT/matrix` 字符串的引用者，
   与 rec01–08（尤其 rec04 BE-float 表）的 ARM 地址交叉比对，找参数表→引擎的绑定关系。
3. c00 6-bit 块：与 E-PL3 block 2 逐字节比对（需合法取得 E-PL3 镜像后走 source-range SHA-256
   合规通道）；若逐字节相同，则可借用前人已排除的结论集继续收窄。
4. c27–c29 特殊图案的消费场景确认（随 1 的反汇编推进）；c30–c39 剖面表的幅值标度（峰值 1027≈1024+ε）
   与显示位深的关系。
